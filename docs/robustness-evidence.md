# Robustness evidence: manipulation and deprecation

Checked against the code on 7 November 2026, on branch `feature/llm-communication-onboarding` on top of `4cbcee4`. The
work is uncommitted. Each row names the code that enforces the control and the tests that prove it, and says what is
still missing.

The **profile** after a test file:
- **FT** is the full-trust test harness in `tests/trust_harness.py`: `full_trust_profile=True`,
  `customer_identity_mode=oidc`, and separate synthetic IdP, proofing and signing providers.
- **DEV** is the default development flow in `tests/flow.py`.
- **UNIT** means no server is involved.

A passing test shows that a mechanism works with synthetic parties. It proves nothing about legal compliance or about
production behaviour.

## 3. Residual risk statement

The full-trust prototype held against every manipulation we tested: 273 targeted test cases passed in this check. They
cover forged metadata and callbacks, replay, scope escalation, wrong-customer actions and direct `OPENED` attempts.
Every counterparty in those tests is synthetic or a mock, so they show that the mechanism works. They do not show how a
real eID, signer, custodian or partner bank behaves. The language model is contained by structure, not by its prompt:
it can only propose tool calls and fact identifiers, and it was evaluated live on only 19 questions, all handled
safely ([../evaluation/final-live-llm/README.md](evaluation/final-live-llm/README.md)). A misleading
sentence without a checkable value would pass the pattern check, but it cannot reach a customer, because released
answers are built from verified facts and fixed texts. Open findings remain:
- F-2: the default environment is development;
- F-3: the older REST handoff route takes the link host from the request;
- F-4: there are no rate limits;
- F-6: the audit trail is append-only but not tamper-evident;
- F-7: some comments claim more than was tested.

F-5, the last server error on malformed callback headers, was fixed on 7 November 2026.

F-1 remains only in the default development profile; the full-trust profile refuses the DEV sign-in at start-up.
Review decisions come from two static synthetic operators, with no staff authentication. Before any production use, each
of these needs an owner, and every real provider integration needs its own threat model and penetration test.

## 5. Worked example: provider API v2 changes or becomes unavailable

**The starting point** in the full-trust journey. The bank hands the application to the depot provider only after
three things: the customer confirmed the exact action, the mandatory checks passed, and the contract package is signed
(`OnboardingService.submit_application`, `TrustGates.submit_missing`). The agent asks for the submission with its
delegated `submit_after_consent` token. The bank decides.

1. **The request.** `VersionedDepotAdapter` asks in v2, the first of `SUPPORTED_VERSIONS`. It sends references only:
   the application, provider, product and channel ids, with `idempotency_key` set to the application id.
2. **What the provider can do, and what the bank does in each case** (rows of
   [../evidence/provider-compatibility-matrix.md](evidence/provider-compatibility-matrix.md)):

   | Provider behaviour | Row | What the bank does |
   |---|---|---|
   | v2 changes the shape of its answer, or adds a field such as `opened` | E, G | `parse_submission_response` raises `ProviderContractViolation`. The refusal is `contract_violation`. The bank does **not** retry in v1, because the provider may have acted |
   | v2 is retired, and the answer names v1 as a fallback | C | `COMPATIBILITY_POLICY` allows v2 to v1, so the adapter asks again in v1. On acceptance the application moves to `SUBMITTED_TO_DEPOT_PROVIDER`. The audit event `application.submitted` records `contract_version: v1` and `fallback_from: v2`, and the log gets a warning `version_unavailable`. Consent, checks and signature are neither repeated nor lowered, because they ran before the adapter |
   | v2 is retired without a named fallback, or the provider offers only a version the bank does not support | C2, D | The refusal is `no_supported_version` |
   | v2 times out, or the connection is lost | F2, F1 | The refusal is `provider_unavailable`. The bank does not retry in v1 |

3. **On every refusal:**
   - **The agent** receives HTTP 502 with the code `provider_unavailable` and the fixed message "The depot provider is
     currently unavailable." Its status view stays `IN_PROGRESS` (`test_acceptance_d_to_h_a_failed_integration_advances_nothing`).
   - **The audit** alone holds the exact reason: the event `application.submit_denied` with `missing: provider_accepted`,
     plus `contract_version` and `refusal`.
   - **The application** stays in `CONTRACT_PENDING`, and no `depot_submissions` row is written.
   - **A correctly signed provider confirmation** is now refused with 403, because nothing was handed over.
4. **Recovery.** The agent can submit again later with the same delegation, and when the provider answers, the journey
   continues to `OPENED` through the signed callback (`test_the_same_application_can_continue_after_the_provider_recovers`).
   The bank never retries by itself. There is no scheduler, no failover to another provider and no reconciliation call.
5. **A person.** A depot refusal opens no review case by itself. The customer can ask for a person on the bank's page
   at this step: `CONTRACT_PENDING` is one of the steps that a customer's request can pause. The code sends the
   customer no message about the refusal.
6. **What is not built.**
   - Reconciling an unknown outcome after a real timeout (decision D14).
   - Signed version metadata and sunset dates in the provider's manifest (concept only).
   - Deduplication by the provider: v1 carries the application id and v2 an explicit idempotency key, but whether a
     real provider deduplicates was never tested.

   The provider is an in-process mock, so a timeout is a raised error, not a real wait.
